# Design notes

## Database schema

One table, `qa_records`, created by the Alembic migration `alembic/versions/0001_create_qa_records.py`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key, generated by the database (`gen_random_uuid()`) or by the app |
| `question` | `text`, not null | The question **as submitted** (only leading/trailing spaces trimmed) |
| `normalized_question` | `text`, not null | Lower-cased with whitespace collapsed. The Redis cache key is built from this |
| `answer` | `text`, not null | The answer that was returned |
| `cache_hit` | `boolean`, not null, default `false` | `true` if the answer came from Redis instead of being generated |
| `created_at` | `timestamptz`, not null, default `now()` | **Indexed** (`ix_qa_records_created_at`), because history is always read newest-first |

Both the original and the normalized question are stored. The original is what the user
actually typed, so history shows it faithfully; the normalized copy is what makes
"What is the capital of France?" and "what is  the CAPITAL of france?" count as the same
question.

## Why one table instead of separate `questions` and `answers` tables?

For this application every question has exactly one answer, and the answer has no identity or
life of its own:

- **It is a one-to-one relationship.** Splitting a one-to-one relationship adds a second table,
  a foreign key and a join to every read, and gains nothing: no column is shared and nothing is
  stored once instead of twice.
- **The two halves are always created and read together.** A submission is inserted in one
  statement into one table. With two tables it would need two inserts inside one transaction
  (to avoid a question with no answer), and `GET /history` would need a join to show the pair.
- **No integrity problem is being solved.** Normalisation removes duplicated data and update
  anomalies. Here there is nothing to deduplicate: each row is an immutable record of one
  submission, so there is no value that has to be changed in several places.
- **It is simpler to index and query.** The only access pattern is "newest N records", which
  one index on `created_at` serves directly.

Separate tables become the better design if the relationship stops being one-to-one, for
example if one question can have **many answers** (regenerated answers, answer versions,
answers from different models), or if questions are **shared and deduplicated** across users.
Neither applies here, and adding a table later is a straightforward migration.

## Repeated questions: which strategy?

The three options, and the choice:

| Option | Behaviour | Problem |
|---|---|---|
| A. New row every time, no extra info | Simple history | Cannot tell a generated answer from a cached one |
| B. Reuse the existing row | One row per distinct question | Loses how often and when a question is asked; needs a lookup and a uniqueness rule; the history is no longer a log |
| **C. Return the cached answer but still save a separate submission row** | History is a complete log of submissions | Slightly more rows (one small insert per request) |

**Chosen: C.** The history table is an audit log of what users asked, so every submission is
recorded, with `cache_hit` showing whether Redis served it. This keeps the data honest:

- Nothing is lost when a cache entry expires (the TTL is one hour), because the database does
  not depend on the cache.
- It is easy to measure the cache: `SELECT avg(cache_hit::int) FROM qa_records` gives the hit
  rate.
- A cache hit never calls the model, so cost and latency are unchanged by also saving a row.
- If the model's answer to the same question changes after the cache expires, the history
  shows both answers, in order.

## Request flow

```
POST /ask
   │
   ├─ 1. Check Redis (key = sha256 of the normalised question)
   │        │
   │        ├─ HIT  → return the cached answer (no generation)
   │        │         save a history row with cache_hit = true
   │        │
   │        └─ MISS → 2. generate the answer (Gemini)
   │                  3. save the row in PostgreSQL (cache_hit = false)
   │                  4. cache the answer in Redis with a TTL (default 1 hour)
   │                  5. return the answer
```

Failure handling:

- **Redis down or not configured:** reads count as a miss and writes are skipped, with an error
  logged. The API still generates and saves answers.
- **PostgreSQL down:** the answer is still returned and the failed save is logged. `GET /history`
  returns 503.
- **Generation fails** (timeout, quota, bad key): the error is returned (504 / 429 / 502) and
  nothing is saved or cached, so a failure is never served from the cache.
